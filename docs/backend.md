# Shiftline backend

The manager and worker web apps use one Supabase project: `hfhiuxijpbujoahtnkjt` (PostgreSQL 17). The database is authoritative for identities, permissions, attendance, tasks, conversations, approvals, calculations and audit history. Neither a publishable key nor an employee number confers manager access.

## Database and API

The authoritative schema is the ordered SQL history in `supabase/migrations/`. Seventeen migrations are applied to the hosted project as of 13 October 2026. `shared/database.types.ts` is generated from that hosted schema and used by both web clients. Generate it again after schema changes.

The public application API has two authenticated RPCs:

- `sl_snapshot()` returns the current account's permitted records and company-local date. `schemaVersion: 11` identifies the current contract.
- `sl_command(p_action, p_data)` validates an object payload, derives identity from `auth.uid()`, validates database membership and applies a mutation in one PostgreSQL transaction. It returns an updated scoped snapshot.

Direct table access is denied to `anon` and `authenticated`. All 30 application tables have RLS enabled. RLS intentionally has no permissive policies: clients use scoped RPCs. The privileged implementation lives in the non-exposed `shiftline_private` schema, has an empty search path, and checks authenticated database membership. Only its current snapshot/command entry points and the company-topic authorization predicate are executable by `authenticated`; archived implementation functions are not.

## Integrity and concurrency

Composite foreign keys enforce company ownership for employee/site, shift, job, sender/recipient, author, reviewer, device and calculation references. Additional keys enforce employee ownership of shifts and matching shift ownership of events, corrections, devices and approved calculations. Join tables without a company column validate the corresponding parent ownership.

Attendance inserts lock the owning shift and validate the state machine and event chronology at the database layer. Authenticated company mutations serialize using the existing company lock; activation additionally uses a per-user advisory lock. Two clock-ins cannot both succeed for the same shift. Board moves use the expected previous status to detect a stale write and never create attendance events. A task already moved to In progress can still be started by its assigned worker.

Foreign-key lookups have covering indexes. Frequently used company/date, task-status, pending request/submission and audit queries have dedicated indexes. The unused-index advisor is expected on the currently empty hosted database; do not remove ownership/FK indexes merely because traffic has not started.

## Location privacy

Foreground `report_position` calls require the worker's own active shift, acceptable GPS accuracy and an open company-local tracking window. The target is the workplace while working, or the attendance-linked job location while on a job. Managers receive the latest on-duty worker position, its accuracy, timestamp and job context. Workers and other companies cannot read positions. There is one current point per worker and no route history. Positions expire from snapshots and map markers after three minutes; hosted `pg_cron` physically prunes expired/off-duty points every minute. Confirmed attendance transitions remove the old point immediately. Turning sharing off, hiding the tab or losing connectivity stops browser GPS and attempts a position clear; abrupt closure or connection loss relies on server expiry.

Only clock-in submissions may retain a GPS stamp within the bounded shift capture window. Lunch, personal departures and clock-out discard supplied coordinates before saving evidence. Raw position reports are not written to location history. An offline replay uses the same sanitized payload for idempotency.

Web sharing requires an open, visible, connected worker app and location permission. The browser watches for changes and requests fresh evidence each minute on stationary devices. Lunch on a job keeps the job open, clears its position, and resumes `on_job` after lunch. Job coordinates are configured by the manager; a job without coordinates cannot send map positions. Physical-device GPS accuracy, mobile browser permission behavior and abrupt-close expiry still need acceptance testing.

## Real account setup

Manager and worker entry points now require real Supabase accounts in development and production. The manager signs in, creates the company and adds workers. Workers create and confirm their account, then join with only the manager's one-time access code. `join_workplace` validates the code against the manager-created employee record, reads display/contact details from the authenticated Auth user and exposes them to that company's manager. Metadata never grants roles or company membership. Both apps must use the same Supabase URL and publishable key.

Development and production both use authenticated Supabase accounts. Local account endpoints, automatic test logins, reusable test codes and sample-record screens have been removed. The SQL test harness in `scripts/test-database.mjs` uses isolated fixtures and is never imported by either application. The obsolete mock native prototype was removed; the actual Expo attendance client remains in `mobile/`.

Both web apps share the same typed backend and independently stored sessions. `sl_command` emits a private `refresh` notification after a successful command. The notification carries no application records (Supabase adds only a generated message ID). The `realtime.messages` SELECT policy and `shiftline_private.can_receive_updates` predicate require authenticated membership in the topic's company. Clients cannot publish through this policy. Clients re-fetch scoped RPC snapshots rather than trusting broadcast data. Visible-tab polling every 15 seconds and focus/reconnection refresh recover dropped messages. Realtime initializes daily notification partitions on its first connection; commands remain durable when notifications are unavailable.

The real workspace is Plug & Play, Africa/Windhoek. The supplied workplace link identifies 22 Copper Street, Prosperita, Windhoek at -22.6226793, 17.087781. Its existing 150m radius, 100m accuracy limit, geofence mode and company policy flags were preserved while saving the coordinates. Manager settings remain accessible from the account menu; attendance policies are not a sidebar destination.

`supabase/tests/backend_smoke.sql` exercises those shared paths on hosted PostgreSQL with temporary fixture users and companies. It finishes with `ROLLBACK`, so no test records remain. It passed against this project on 12 October 2026, including company-topic authorization and private database notifications. Run the whole file as one transaction; never run extracted fixture statements separately.

Supabase advisors report no missing foreign-key indexes. They report informational RLS-without-policy findings for the intentional RPC-only access model. One Auth warning remains: leaked-password protection is disabled. Enable it in Supabase Auth before launch: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection . Hosted SQL verification does not prove email delivery, real user login or physical-device GPS behavior.

## Backup and release procedure

Apply migrations before deploying matching app code. Migration filenames match hosted history; do not edit applied SQL. The local adapter identifies migrations by their descriptive suffix so aligning filenames with hosted timestamps does not apply existing migrations twice.

Database backups are separate from source control and CSV exports. Automatic daily backups depend on the Supabase plan; their availability and restore history have not been verified for this project. Confirm them in https://supabase.com/dashboard/project/hfhiuxijpbujoahtnkjt/database/backups/scheduled . Pro/Team/Enterprise have scheduled backups; free projects need regular off-site exports. Point-in-time recovery is a paid option and has not been enabled here. See https://supabase.com/docs/guides/platform/backups . Storage file contents need a separate backup if uploads are introduced.

Before client data is added, agree backup retention, store an off-site export securely and test a restore in a separate project. For application rollback, redeploy the previous app while retaining additive schema and immutable history. Do not drop attendance/audit tables or reset the hosted database.

## Worker name/phone access

The worker UI collects a company registration code, full name and phone. `worker-access` runs on Supabase Edge with a server-only service-role key, validates contact fields, charges durable registration limits (including invalid code attempts), provisions a confirmed internal `SL-number@workers.shiftline.invalid` Auth identifier, and calls service-only `sl_worker_register`. This identifier is technical and is never stored as employee contact email. No email/SMS is sent, and the supplied phone is not marked verified. The service deletes only its newly created Auth identity if enrollment fails; an uncertain cleanup is logged for operator attention. SQL fixes role to employee, resolves the company by its registration code, derives its manager's default site, and prevents duplicate phone enrollment within that company.

`access_status` gates the authoritative snapshot, every company command and private Realtime authorization. Pending/rejected workers receive only their own name, number, phone and status. Manager Team receives registrations on the existing private invalidation channel/fallback polling. Approval has an expected-status concurrency check and an audit entry. Workers poll their own status until approved. Generated codes are shown once before sign-in and never persisted in local preferences or employee records. Login uses native Supabase password sessions, refresh and rate limits. Lost codes require verified manager JWT and same-company SQL authorization; replacement updates the native Auth password and records an audit. Already signed-in sessions are not revoked by code replacement.

The current worker UI uses company-code enrollment and number/code sign-in. Older invitation RPCs remain for compatibility, but implicit single-company registration fails closed. Each Auth account belongs to one company; account switching between multiple memberships is not implemented. Company profiles can be changed only by active managers in that company. Logos use a private `company-logos` bucket, 1 MB PNG/JPEG/WebP uploads, membership-scoped Storage policies, and one-hour signed display URLs. Worker snapshots do not expose the company recruitment code. Run `npm run test:tenancy` for enrollment, profile, logo and cross-company regression tests.

## Scheduling, directory and job operations

`assign_shift` is idempotent for the same employee/day and schedule. A different duplicate returns a clear Calendar edit instruction. `update_shift` uses the expected original schedule to reject stale manager edits. Shifts with recorded/submitted attendance, reviewed timesheets or locked periods cannot be edited; assigned jobs must remain within the revised shift. Every shift pins its policy version.

Employees have department (`team`), work role (`job_title`), bio and optional HTTPS photo URL. Company managers edit these through `update_employee_profile`, without changing login roles or workplace approval. Employees replaces Audit in navigation; append-only evidence stays in the backend. Photos use URLs; file upload/storage is not implemented.

Job creation accepts a client UUID for safe retry. Briefs include destination, instructions, coordinates, boundary radius, lunch plan and overtime flag. Coordinates/plans may be edited before the job starts. The lunch plan informs workers; it never prevents a worker from recording a real lunch or sharing its private location. An overtime flag does not approve payable overtime. Extend the assigned shift to cover later work before scheduling an overtime job. The primary assigned worker records job attendance; other job members collaborate on the checklist/comments and do not record attendance against another worker's shift.

Task-board moves cannot move a worker's active job to Planned or Done. The worker must return from the job first, including ending lunch if on a break. Frontend active-job context follows attendance events rather than board status. Company announcements open complete worker detail sheets, with server-recorded acknowledgements when requested. Both web UIs use the installed Radix Select primitive through one styled component, with keyboard support, form submission and reset behavior.

Hosted `workplace_operations_smoke.sql`, `shift_scheduling_smoke.sql` and the general smoke tests run fixture-only transactions ending in rollback. No test workers, attendance or jobs are deployed.
